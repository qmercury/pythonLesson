# 교사용 MQTT·IoT 입문 교재

> **교사도 처음 배우는 것을 전제로 만든 수업 가이드.** 학생들에게 바로 읽어 줄 쉬운 설명, 교사가 알아야 할 정확한 개념, 시연·질문·답변, 실습 확인 방법을 함께 제공한다.

- 대상: 초등 4~6학년 / SPIKE Prime Python 기초 + Tkinter 기본
- 시간: **90분 × 12차시**
- 목표: Tkinter 앱 → MQTT → 다른 PC → (추후) EV3 Legendary 블루투스 직렬통신까지 연결
- 준비 순서: **교사 단독 이해·시험 → 두 PC 실습 → 학생 팀 실습 → 실물 로봇 연동**
- 단계 구분: PC 간 MQTT 예제와 가상 로봇은 작성됨. **Pybricks Legendary 실제 명령 송수신 어댑터는 아직 구현·검증 전.**
- 교사 첫 수업 전: [교사 실습·점검표](TEACHER-PRACTICE.md) → [1차시 자료](lessons/lesson-01.md).

## 1. MQTT를 한 문장으로

**MQTT는 장치끼리 직접 연결하지 않고, '브로커'에 메시지를 보내고 필요한 메시지를 구독하는 방식의 통신 프로토콜이다.**

### 아이들에게 설명할 비유: 학교 방송실

- **Publisher(발행자):** 방송할 내용을 보내는 반
- **Broker(브로커):** 방송실. 누가 어떤 방송 채널을 구독했는지 관리하고 전달
- **Subscriber(구독자):** 방송을 듣기로 한 반
- **Topic(토픽):** 방송 채널 이름
- **Payload(페이로드):** 실제 방송 내용(예: `forward`)

브로커가 로봇 명령을 **직접 실행하지는 않는다**. 명령을 실행하는 것은 수신 프로그램과 로봇이다.

```text
[학생 A / Tkinter]  -- publish(cmd) --> [MQTT 브로커]
         ^                                     |
         |                                     | deliver(cmd)
         |                                     v
         +-------- subscribe(status) -- [학생 B / 수신 프로그램]
                                                    |
                                              (나중에 연결)
                                                    v
                                 [Bluetooth 직렬] -- [EV3 Legendary]
```

**확인 질문**
- 방송을 보내는 사람은? → 발행자
- 어느 메시지를 들을지 무엇으로 선택하나? → 토픽 구독
- 브로커가 직접 모터를 돌리나? → 아니다. 수신 프로그램이 실제 명령을 처리한다.
- A와 B가 서로의 IP를 알아야 하나? → 둘 다 브로커에 접속하므로 보통 브로커 주소만 알면 된다.

## 2. 용어 카드: 교사가 먼저 익힐 것

| 용어 | 교사용 정확한 뜻 | 학생용 한 문장 |
|---|---|---|
| IP | 네트워크에서 장치를 찾아갈 주소 | 컴퓨터의 네트워크 주소 |
| Broker | 접속·구독·배달을 관리하는 MQTT 서버 | 메시지 중계 방송실 |
| Client | MQTT 서버에 연결하는 앱/장치 | 방송을 보내거나 듣는 프로그램 |
| Publish | 특정 토픽으로 메시지를 발행 | 방송 보내기 |
| Subscribe | 특정 토픽의 메시지 수신 신청 | 채널 구독하기 |
| Topic | 계층 구조를 가진 메시지 분류 문자열 | 방송 채널 이름 |
| Payload | 메시지의 실제 바이트 데이터 | 방송 내용 |
| Callback | 특정 이벤트가 생길 때 실행되는 함수 | 일이 생기면 자동 실행되는 함수 |
| JSON | 키와 값으로 구조화한 텍스트 형식 | 항목 이름이 있는 명령 카드 |
| QoS | MQTT 메시지 전달 시도/확인 방식 | 전달 확인 방법 |
| Retained | 브로커가 토픽의 마지막 메시지를 보관 | 나중에 온 사람도 보는 마지막 공지 |
| Latency | 명령이 전달되는 데 걸리는 지연 | 전송에 걸리는 시간 |
| Serial | 순서대로 바이트를 주고받는 통신 | 글자를 차례대로 보내는 통로 |

## 3. Topic과 Payload를 정확히 이해하기

```text
Topic:   robottagram/class01/robot01/cmd
Payload: {"action": "forward"}
```

- `robottagram`: 프로젝트 이름
- `class01`: 교실 구분
- `robot01`: 로봇 구분
- `cmd`: 명령 토픽. 수신 PC가 구독
- `status`: 수신 결과 토픽. 조종 PC가 구독

**중요:** 구독자에게 메시지가 전달되더라도 로봇이 성공적으로 움직였다는 뜻은 아니다. 성공 여부를 알려면 수신기가 별도의 상태 메시지를 발행해야 한다.

교사 예제의 실제 명령은 `action` 외에도 메시지 ID, 생성 시간, 요청 지속시간, 제한 속도가 들어 있다. 학생에게는 단순한 `forward` 문자열을 먼저 보여 주고 나중에 JSON 필드를 늘리면 좋다.

## 4. QoS / Retain / 연결 끊김

| 기능 | 의미 | 수업에서 강조할 점 |
|---|---|---|
| QoS 0 | 최선 노력 전달, 재전송 확인 없음 | 상태 표시처럼 놓칠 수 있는 정보에 사용 가능 |
| QoS 1 | 최소 1회 전달을 목표로 확인·재전송 | **같은 명령이 중복 도착할 수 있다** |
| QoS 2 | MQTT 전달 단계에서 정확히 한 번을 목표 | 물리 모터 실행까지 정확히 한 번 보장하는 것은 아님 |
| retained = True | 새 구독자에게 보관된 마지막 메시지를 보낼 수 있음 | **이동 명령에는 사용하지 않는다** |
| retained = False | 마지막 메시지로 보관하지 않음 | 제어 명령 기본값 |
| 연결 끊김 | 통신 경로 일부가 중단됨 | **로봇 자체의 자동 정지**가 필요 |

**교사 메모:** QoS 1이라고 안전한 것은 아니다. 중복된 `forward`를 두 번 실행하면 로봇이 예상보다 멀리 갈 수 있다. 수신 프로그램에서 `id` 중복 검사를 하는 이유다. MQTT의 성공 ACK와 실제 모터 실행 성공 ACK도 다르다.

## 5. Python 코드가 동작하는 흐름

```text
① MQTT 클라이언트 객체 생성
② on_connect / on_message 콜백 함수 등록
③ 브로커 연결 시작
④ loop_start(): 별도 네트워크 스레드에서 메시지 처리
⑤ 메시지가 오면 콜백이 queue에 넣음
⑥ Tkinter root.after(...)가 queue를 읽고 화면 변경
⑦ 버튼을 누르면 publish(...)로 명령 발행
⑧ 종료 시 disconnect() / loop_stop()
```

**왜 queue가 필요한가?** Tkinter 위젯은 메인 UI 스레드에서 갱신하는 것이 안전하다. Paho MQTT의 `loop_start()`는 네트워크 처리를 다른 스레드에서 실행하므로, 콜백에서 Tkinter `Label.config()`를 바로 호출하지 않고 `queue.Queue()`에 넣었다가 `root.after()`로 처리한다.

**교사 설명 문장:** "방송을 듣는 직원과 화면을 그리는 직원이 서로 다른 일을 해요. 받은 방송을 메모함(queue)에 넣으면 화면 담당 직원이 가져가서 보여 줍니다."

## 6. MQTT와 Bluetooth 직렬통신은 서로 다른 계층

| 경로 | 역할 |
|---|---|
| 학생 A ↔ 브로커 ↔ 학생 B | 네트워크 MQTT 통신 |
| 학생 B ↔ EV3 Legendary | **Bluetooth Classic 직렬통신** |
| EV3 내부 | 받은 명령 해석·모터/센서 제어 |

**기존 실습 사실:** 로보타그램 손 씻기 스테이션 v8에서 **EV3 Legendary → Chrome Web Serial → 화면 제어**가 동작했다. 하지만 **컴퓨터에서 EV3로 사용자 명령을 전송하여 모터를 움직이는 역방향은 별도 검증**이 필요하다. Web Serial의 성공과 Python `pyserial` 연결의 성공도 동일하지 않다. 상세: [EV3 직렬 연결 설계](../../docs/ev3-legendary-serial.md).

## 7. 수업의 안전한 순서

1. **종이 메시지 카드**로 방송실 역할놀이
2. 같은 PC 또는 두 PC에서 **채팅**; 모터 없음
3. **Tkinter 원격조종기와 가상 Canvas 로봇** 연결
4. **양방향 상태·오류·연결 끊김** 실습
5. 별도 장비 시험 후 **EV3 Legendary** 연결
6. 저속·짧은 이동·자동 정지 검증 후 프로젝트 확장

브로커 1883 포트는 교실 LAN에서만 허용하고 인증·ACL을 사용한다. 외부 인터넷에 노출하지 않는다. 실물 로봇은 **장치 내부 watchdog 및 독립 정지 기능**을 갖춰야 한다.

### 교사용 예상 질문과 짧은 답

**Q. Wi-Fi와 MQTT가 같은 건가요?**  
A. 아니요. Wi-Fi는 통신할 수 있는 네트워크 연결 방식이고, MQTT는 그 위에서 메시지를 교환하는 규칙입니다.

**Q. 브로커가 없으면 MQTT가 안 되나요?**  
A. 일반적인 MQTT 발행/구독에서는 브로커가 필요합니다. 두 PC는 서로 직접 접속하는 대신 브로커와 통신합니다.

**Q. 왜 토픽을 구분하나요?**  
A. 다른 팀의 명령이나 센서 데이터가 섞이지 않게 하기 위해서입니다. 단, 토픽 이름만으로 접근 권한이 생기는 건 아니며 서버의 ACL도 필요합니다.

**Q. 그럼 메시지가 도착하면 모터는 반드시 움직이나요?**  
A. 아닙니다. 명령 검증, 모터 연결, 배터리, 상태 등에서 실패할 수 있어 실제 결과를 다시 보내야 합니다.

**Q. 전진을 계속 누르고 있는데 네트워크가 끊어지면요?**  
A. 원격 STOP은 도착하지 않을 수 있으므로 실제 로봇은 **자체 시간 제한 후 자동 정지**하게 만들어야 합니다.
